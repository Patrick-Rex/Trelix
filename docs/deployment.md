# Trelix 生产部署

本文规定首版 Linux Docker 交付、外部配置、持久化与恢复契约，部署资产位于目标目录 `deploy/docker`。交付验收属于 [M6](milestones.md#阶段与依赖)，可执行命令与配置清单随实际发布物提供并验证。

## 交付与运行边界

- 首版面向 Linux Docker，采用单容器、单个 Server 实例，前后端统一交付。
- 前端生产构建产物由 Server 提供静态资源服务；同一服务入口提供管理与应用 API。
- 生产运行不依赖 Node.js 开发服务器、Vite 或 Aspire AppHost；AppHost 用于本地开发编排。
- SQLite 数据通过容器外部挂载持久化；替换镜像和重建容器不能清空业务数据。
- .NET SDK 由业务应用集成并在业务应用进程中运行，不作为配置中心容器内的独立服务。

系统边界见 [架构设计](architecture.md#系统边界)。单实例是首版交付范围，不以多个 Server 实例共享同一数据文件扩展该范围。

## 外部配置与凭证

- 镜像不包含环境专属连接地址、真实业务配置、管理员初始化密码或应用令牌。
- 部署参数通过环境变量及外部密钥注入；管理访问使用 HTTPS，登录 Cookie 使用 HttpOnly 与 Secure，管理写请求执行防伪造校验。
- 首个管理员只在没有管理员时使用外部初始化凭证创建；重启与升级不覆盖已有账号。
- 业务应用分别配置 Trelix 地址、项目、环境、文件和应用只读令牌，在首次拉取前完成凭证注入；启动必须成功取得该文件的已发布配置。
- Trelix 业务配置环境与 ASP.NET Core 运行环境分别管理；生产应用不依赖 `launchSettings.json`。

认证与令牌行为统一见 [首版认证与访问控制](product-plan.md#首版认证与访问控制)。

Server 已采用 `Trelix:Storage:DataDirectory` 配置数据目录，非 Development 环境必填；初始化凭证键为 `Trelix:Administrator:Username` 和 `Trelix:Administrator:Password`。环境变量中的冒号替换为双下划线。已有管理员时不再需要初始化凭证；账号不存在且凭证缺失或不符合初始化要求时，Server 启动失败。实际容器注入和挂载操作仍随 M6 发布物验证。

## 数据持久化与恢复

持久化与备份覆盖 SQLite 中的配置身份、草稿、发布内容、历史版本、当前发布指向、管理员及应用令牌授权信息。备份具有与在线数据相同的保密要求，不进入源码或公开交付物。

当前实现将 `trelix.db` 与 Data Protection 的 `keys` 子目录放在同一数据目录；会话记录也存于 SQLite。密钥文件由平台生成，未配置额外的静态加密服务，目录须仅允许运行身份和获授权的备份身份访问。保留密钥才能在重启后继续验证已有 Cookie；备份须覆盖整个数据目录，SQLite 在线备份还需处理其伴随文件，不能随意复制正在写入的单个数据库文件。Server 在开始服务前自动应用迁移，升级前须完成可恢复的备份。

部署交付必须包含与实际实现一致的挂载目录、数据库位置、备份和恢复操作说明。恢复以数据可用性验证为准：检查已发布配置、历史版本、管理员登录和应用授权读取；仅证明数据库文件存在不能构成恢复验收。

替换镜像、容器重建和数据恢复均按 [AC-09](quality.md#ac-09-生产交付) 验证。数据库结构变化与迁移使用真实 SQLite 检查，不能套用其他数据库的恢复行为。

## 部署交付要求

M6 的发布物同时提供实际构建入口、容器启动参数、外部配置清单、持久化挂载说明、备份恢复步骤和验证结果。文档中的命令、路径与配置键必须来自实现并经目标环境验证。

生产健康检查的实际暴露范围必须与部署及认证边界一致，并在交付环境验证；本地 Aspire 面板和开发专用地址不作为生产监控入口。日志与遥测遵循 [信息边界](quality.md#ac-10-可观测性与信息边界)。
