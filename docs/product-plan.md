# Trelix 产品方案

本文记录已确认的产品目标、首版范围与业务规则，描述目标行为，不表示相关功能已经实现。[架构设计](architecture.md) 规定程序边界，[技术基线](development-baseline.md) 规定选型，[交付里程碑](milestones.md) 规定交付顺序。完整导航见 [文档索引](README.md)。

## 产品目标

Trelix 面向管理应用配置的管理员和接入配置的 .NET 应用开发者，提供独立运行的轻量级配置中心。管理员负责配置与访问授权，业务应用仅消费授权范围内的已发布配置。

| 编号 | 目标 | 达成标准 |
| --- | --- | --- |
| G1 | 统一管理并隔离项目与环境 | 按项目、环境和文件定位配置；应用仅能读取和监听授权范围内的已发布内容 |
| G2 | 可控发布与可追溯回滚 | 编辑保存不直接影响应用；发布有不可变历史；回滚生成新版本；并发操作不静默覆盖 |
| G3 | 一致且可靠的编辑体验 | JSON/YAML/Tree 编辑同一份数据；无效输入不丢失、不误提交旧数据；文件切换和冲突有明确反馈 |
| G4 | 接入 .NET 原生配置与重载 | 应用继续使用 IConfiguration 与 Options，配置优先级明确，发布可触发配置重载 |
| G5 | 独立部署与持久化交付 | 无外部 IAM 依赖，在 Linux Docker 单容器交付前后端，SQLite 挂载持久化并具备可验证的备份恢复流程 |

各目标的验收场景见 [质量与验收](quality.md#目标与验收映射)。

## 首版范围

首版包含内置管理员登录与退出、应用只读令牌管理、项目/环境/文件管理、JSON/YAML/Tree 编辑、草稿保存、发布、历史与回滚、并发保护、应用读取与长轮询，以及 .NET 配置 SDK。全部能力按 [六个里程碑](milestones.md#阶段与依赖) 交付。

首版采用单实例部署，Linux Docker 单容器统一交付管理界面与 Server，SQLite 通过挂载持久化。管理界面服务于管理员，SDK 服务于业务应用，两者不是同一个交付物。具体职责见 [架构设计](architecture.md#模块职责与依赖方向)。

首版明确不包含：

- 多实例或高可用部署。
- Namespace、Group 等额外配置层级。
- 外部 IAM、OIDC/SSO 或 OAuth 令牌签发服务。
- 多用户管理、管理员分权与 RBAC。
- SDK 多文件合并和本地磁盘配置缓存。
- YAML 注释、锚点名称和原始排版的持久化。
- 替业务应用自动重建连接池、单例对象等运行时资源。

## 产品定位与配置组织

Trelix 是单实例部署的轻量级配置中心，提供配置管理界面、配置分发 API 和 .NET 原生配置集成。

- 配置层级为 Project → Env → ConfigFile，不增加 Namespace、Group 层级。
- 配置文件由项目、环境和文件名共同标识。不同项目或环境下的同名文件分别管理。
- 项目与环境业务标识、文件名按原值区分大小写；长度上限分别为 128、128、256 个字符，项目与环境显示名最多 200 个字符，名称不能为空或仅含空白。允许重命名项目、环境及文件，内部 ID 与现有令牌授权保持不变；应用使用新名称读取配置。
- 项目仅在无环境时可删除；环境仅在无文件且无关联令牌授权时可删除，已撤销或过期令牌的授权关联也计入检查。删除文件会在同一事务中删除其草稿与全部发布历史；之后读取返回 404，同名重建使用新的文件 ID。
- 项目、环境的修改与删除，以及所有文件写操作均校验调用方的并发基准。
- 配置正文统一保存标准 JSON；数据库选型由 [技术基线](development-baseline.md) 维护。
- 配置 JSON 根节点必须是对象；嵌套对象与数组可包含标准 JSON 值，同一对象内禁止忽略大小写的重复属性名，属性名不得含冒号。正文按 UTF-8 计量最多 1 MiB，嵌套深度最多 64 层，服务端原样保存通过校验的正文。
- JSON、YAML、Tree 是同一份 JSON 数据的编辑视图，切换视图不创建新的配置文件或存储格式。
- Web 管理界面目录为 `src/frontend`；面向业务应用的 .NET SDK 是独立交付物，两者职责分开。

## 首版认证与访问控制

首版采用内置管理员账号 + Cookie 登录 + 应用只读令牌。账号与应用令牌的校验信息、授权范围由 Trelix 管理，统一持久化到 SQLite；首版不依赖外部 IAM 平台，不接入 OIDC/SSO 或 OAuth 令牌签发服务。

### 管理员登录

- 首版只有一个内置管理员，管理全部项目和环境；不提供其他管理用户、角色或项目级管理权限分配。
- 管理员使用 Trelix 内置账号和密码登录管理界面，服务端验证成功后通过 ASP.NET Core Cookie 认证建立登录会话。
- 会话固定有效期为 8 小时，不自动续期；退出立即使当前服务端会话失效，其他会话不受影响。浏览器 Cookie 不设置持久化登录。
- 首个管理员使用部署时从源码之外注入的初始化凭证创建；初始化仅在没有管理员时执行，不设置通用默认密码，也不在重启时覆盖已有账号。
- 首次启动缺少有效初始化凭证时拒绝提供服务；账号名为 1–128 个字符且无首尾空白，初始化密码为 12–1024 个字符。登录接口按来源 IP 使用令牌桶限流：初始及最大容量为 10，每 6 秒补充 1 个令牌，每次请求消耗 1 个；令牌耗尽时不排队，立即返回 429。
- 密码使用安全的密码哈希保存，不存储明文或可还原的密码；复用成熟的密码校验能力。
- 管理 API 使用管理员 Cookie 身份及对应授权策略。登录 Cookie 使用 HttpOnly，生产环境使用 HTTPS 和 Secure Cookie；管理写操作校验防伪造令牌。
- 登录请求也校验防伪造令牌；登录前获取匿名令牌，登录后重新获取绑定当前身份的令牌。
- 管理界面提供登录、退出及会话失效提示；未登录的管理 API 请求返回 401，身份有效但权限不足返回 403，界面据此提示或引导登录。

### 业务应用访问

- 管理员创建应用只读令牌，指定一个或多个明确的项目与环境组合；每个环境必须属于对应项目，不提供隐含的全项目或全部环境授权。业务服务使用独立的应用令牌，不使用管理员账号密码或登录 Cookie。
- 应用令牌采用高强度随机字符串，服务端保存校验摘要及授权信息。创建时必须指定晚于当前时间的有效期；原文仅在创建或轮换成功时返回一次，不要求 JWT 格式或 OAuth 登录交换。
- 撤销立即生效；轮换保持名称与授权范围，指定新有效期，在同一事务中撤销旧令牌并创建新令牌。旧令牌立即失效，已撤销令牌不能再次轮换；并发轮换只允许一个操作成功。
- SDK 在读取与长轮询请求中通过 `Authorization: Bearer <应用令牌>` 携带凭证。Bearer 表示请求头中的携带方式，服务端按应用令牌规则校验。
- 每次读取和监听均检查令牌有效性、项目及环境授权；应用只能读取和监听授权范围内的已发布配置，无草稿读取、保存、发布、回滚或令牌管理权限。
- 无效、过期或已撤销的令牌返回 401，超出授权范围返回 403。服务端不能因为请求中的项目、环境与客户端配置一致就跳过授权检查。

### 凭证注入与验收

- Trelix 地址、项目、环境、文件与应用令牌分别配置，凭证不放入 URL。应用令牌必须在首次拉取配置前可用，不从 Trelix 远程配置中获取自身的访问凭证。
- 本地真实凭证通过 User Secrets 等源码之外的配置注入，部署时通过外部环境或密钥注入。初始化密码、应用令牌及登录 Cookie 不进入镜像、源码、日志或遥测。
- 认证验收覆盖管理员登录与退出、会话失效、管理写操作防伪造校验，以及无令牌、无效令牌、过期、撤销、跨项目和跨环境访问拒绝。
- 应用令牌验收同时覆盖读取与长轮询，并验证它不能访问草稿或调用管理写接口。

## 草稿、发布与版本

- 保存只更新草稿，不影响应用读取的已发布配置。
- 发布将明确选中的草稿修订生成不可变的发布版本；应用只读取已发布内容。
- 草稿修订与发布版本分别管理，保存草稿不触发应用配置更新。
- 发布内容、版本记录和当前发布指向在同一事务中提交；提交成功后通知监听者。
- 保留历史发布版本；回滚使用选中的历史内容生成新发布版本，不修改历史记录或倒退当前版本号。
- 回滚保留当前草稿正文及修订，仅改变当前发布指向与文件并发基准；新发布记录的草稿修订来自源历史内容。历史不可修改，整文件删除时随文件一并删除。
- 保存、发布和回滚均校验调用方携带的基准版本。发生并发冲突时拒绝覆盖，保留编辑内容并提示重新核对。
- 管理 API 承担项目、环境、文件、草稿和发布历史操作；应用 API 承担读取已发布配置和监听变更，两类职责分开。

## 编辑工作区

左侧为环境切换器与项目/文件资源树，右侧为编辑区及保存、发布、历史版本、格式切换工具栏。当前项目、环境和文件始终可见。

编辑状态由统一的文档状态管理，Monaco 与 Tree 通过明确的更新动作交换数据，不互相循环监听。

- 文档状态同时维护当前编辑文本、最后一次有效 JSON 数据、校验结果和修订信息；有效 JSON 数据是各视图共享的数据来源。
- 代码输入防抖解析，只有成功解析且通过校验才更新共享数据；尚未完成或无效的输入保留在文本缓冲区。
- 保存、发布和切换到其他表示格式前立即校验当前输入，不能因为防抖未结束或解析失败而提交上一份有效数据。
- Tree 操作通过统一动作更新文档；同步代码视图时维护光标、选择区、滚动位置及撤销体验，避免每次输入都整体 `setValue()`。
- 切换环境或文件时处理未保存内容；取消失效请求，避免旧响应覆盖当前文件。
- YAML 转为 JSON 后不保留注释、锚点名称和排版等表示信息；视图转换必须保持可表示的数据值，不能静默改变值或类型。
- 服务端独立执行 JSON 校验，不信任浏览器校验结果。

## .NET 配置集成

SDK 最低支持 .NET 10，面向 .NET 10 及以上的业务应用；目标框架与构建约束见 [技术基线](development-baseline.md#已确认的选择)。

SDK 通过自定义 `IConfigurationSource` / `ConfigurationProvider` 接入业务应用现有的配置系统，并由后台服务监听发布变更。提供程序刷新后发出配置重载通知，不重新注册或替换容器中的 `IConfiguration`。此接入方式遵循 [.NET 自定义配置提供程序模型](https://learn.microsoft.com/en-us/dotnet/core/extensions/custom-configuration-provider)。

一次 SDK 接入明确选择一个项目、一个环境和一个配置文件，只读取并监听该文件；首版不提供多文件合并。应用令牌按项目与环境授权，选择单文件不改变服务端的授权范围检查。

连接配置与业务配置分别处理：连接地址、项目、环境、文件和应用只读令牌来自应用本地启动配置，在获取远程内容前确定，远程内容不能修改 SDK 自身的连接目标。SDK 按首版应用令牌协议访问配置 API，不执行管理员登录或向外部身份平台申请令牌。

### 启动与故障策略

- 业务应用启动必须成功拉取所选文件的已发布配置并完成校验，之后才能完成 SDK 接入。请求超时、认证失败、无权访问、没有可用发布内容或响应无效时，启动失败并提供不含敏感信息的诊断。
- 运行中读取或监听失败时保留最近一次成功加载的配置，不清空配置、不用失败响应替换有效内容；后台按退避策略重试。
- 新发布内容完成拉取和校验后整体替换 SDK 的配置快照，再发出配置重载通知。重试或重复响应不产生部分更新。
- 首版不把远程配置保存为本地磁盘缓存；应用进程重启后重新执行首次拉取，不使用上一进程的内存配置启动。

### 配置优先级与消费

业务配置同名键的优先级从高到低为：

1. 命令行参数。
2. 环境变量。
3. Trelix 已发布配置。
4. User Secrets（宿主启用时）。
5. 本地 JSON 配置，其中环境专用文件覆盖通用 `appsettings.json`。

SDK 显式安排提供程序顺序，保留部署参数覆盖远程配置的能力；不能仅在默认配置源末尾追加远程源。后添加的源优先这一机制见 [ASP.NET Core 配置说明](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0)。

业务可以继续使用原生 `IConfiguration` 与 Options 绑定。需要热更新的消费者使用 `IOptionsMonitor<T>`，或在新作用域中使用 `IOptionsSnapshot<T>`；普通 `IOptions<T>` 不承担运行时刷新。已创建的连接池、单例对象或只在启动时读取的配置，由业务应用负责重新应用。Options 的行为见 [官方说明](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/options?view=aspnetcore-10.0)。

## 本地调试与运行时注入

- `launchSettings.json` 用于本地调试 Profile，支持全本地调试与本地业务连接远程开发环境；切换环境不需要修改业务 `appsettings.json`。
- Trelix 的业务配置环境与 `ASPNETCORE_ENVIRONMENT` 分别表示配置选择和 ASP.NET Core 运行环境，二者不要求相同。
- Aspire 通过 AppHost 显式传递连接信息；单独创建一个 Profile 不会自动完成 Trelix 配置注入。
- Docker 镜像不包含环境专属连接地址、凭证或真实业务配置；部署时通过环境变量及外部密钥注入运行参数。
- `launchSettings.json` 中只保存可提交的非敏感启动设置，真实凭证从源码之外注入。

`launchSettings.json` 由本地启动工具使用，发布后的应用不依赖该文件；参见 [ASP.NET Core 运行环境说明](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/environments?view=aspnetcore-10.0)。
